Guía de mitusalud

Qué hace cada pieza del proyecto y, sobre todo, por qué está así. Pensada para alguien que empieza.

Actualizada el 26/09/2026 · Estado: peso y agua con el modelo definitivo (observation + detalle), tests e integración continua

1. Qué es mitusalud y cómo encaja todo

mitusalud es un diario personal de salud: alimentación, sueño, actividad, gimnasio, medicación, analíticas… Cada persona lo instala en su propio servidor y guarda allí sus datos. No es un servicio compartido: cada instalación tiene un único propietario.

Hoy existe la primera pieza que funciona de punta a punta: registrar tu peso y verlo en una lista. Todo lo demás crecerá sobre ese esqueleto.

Construido poco a poco, a propósitoEl peso ya usa el modelo definitivo: una tabla común observation para cualquier registro y una tabla de detalle peso (sección 6). Otras piezas (login, evitar duplicados, auditoría, historial de ediciones…) están identificadas pero se construirán cuando aparezca la función que las necesite, para no diseñar de más. Las decisiones y sus motivos están en docs/MODELO_DATOS.md.

La base de datos vive en un servidor con Docker, así en tu PC no instalas ni Docker ni PostgreSQL. Los dos se hablan a través de un túnel SSH (lo explica la sección 6).

2. Principios

Estas reglas explican casi todas las decisiones del proyecto. Cuando dudes de por qué algo es así, empieza por aquí.

PrincipioQué significa en la práctica
No sobredimensionarUna tecnología entra cuando hay una necesidad real, no "por si acaso". Cada pieza extra hay que instalarla, configurarla, entenderla y protegerla.
Sencillo antes que fácil"Fácil" es lo que parece rápido hoy (un generador mágico, una librería que lo hace todo). "Sencillo" es lo que tiene pocas piezas y poco enredadas. Elegimos lo sencillo aunque cueste un poco más al principio.
Comprensible para un juniorEl código lleva comentarios que explican por qué, no lo que ya se lee en el código.
DTOs mínimosNada de cinco clases por concepto. Una entidad y, como mucho, un record de entrada y otro de salida, de una línea cada uno. Conversión a mano, sin librerías de mapeo.
Paso a pasoPrimero un esqueleto mínimo que funciona de punta a punta; después crece con cada necesidad.

La lista completa de tecnologías, con su estado (aprobada, propuesta o descartada), está en docs/STACK.md.

Maven: qué es

Maven hace dos trabajos:

  • Descarga las librerías que declara el pom.xml (Spring, el driver de PostgreSQL…), y las librerías que esas librerías necesitan. Las guarda en ~/.m2/repository para no descargarlas otra vez.
  • Construye el proyecto en fases siempre en el mismo orden: compile → test → package (crea el .jar) → verify. Si pides una fase, se ejecutan también todas las anteriores. Por eso ./mvnw verify compila y pasa los tests.

.mvn/, mvnw y mvnw.cmd: el Maven Wrapper

Es la respuesta a "¿por qué no tengo que instalar Maven?".

  • mvnw y mvnw.cmd son dos scripts pequeños (uno para Linux/macOS/Git Bash, otro para Windows) que hacen lo mismo que el comando mvn.
  • La primera vez leen .mvn/wrapper/maven-wrapper.properties, descargan exactamente la versión de Maven que dice ahí (ahora la 3.9.16) y la guardan en ~/.m2/wrapper. Las siguientes veces la reutilizan.
  • Resultado: cualquiera que clone el repo usa la misma versión de Maven, sin instalar nada. Se acabó el "en mi máquina compila".

La carpeta empieza por punto (.mvn) porque en Linux eso la oculta: es configuración de herramientas, no código que tengas que tocar.

.gitattributes: por qué importan los saltos de línea

Windows termina cada línea con dos caracteres invisibles (CRLF); Linux, con uno (LF). Git puede convertirlos al descargar, y eso rompe mvnw en Linux: la primera línea #!/bin/sh pasaría a terminar en un carácter extra y Linux respondería bad interpreter.

/mvnw  text eol=lf     # mvnw siempre con saltos de Linux
*.cmd  text eol=crlf   # los .cmd siempre con saltos de Windows

Además, mvnw está marcado en git como ejecutable, para que en Linux funcione ./mvnw sin hacer chmod +x.

pom.xml: dependencia por dependencia

El pom.xml hereda de spring-boot-starter-parent. Ese "padre" fija versiones compatibles entre sí de cientos de librerías; por eso casi ninguna dependencia lleva número de versión. Un starter es un paquete que agrupa todo lo necesario para una tarea (por ejemplo, starter-webmvc trae el servidor web, Jackson para JSON, etc.).

Al final del pom.xml, spring-modulith-bom fija la versión de Spring Modulith (como hace el padre con Spring) y spring-boot-maven-plugin añade el comando spring-boot:run y empaqueta la app en un único .jar ejecutable.

Justo antes de <build> está el bloque <profiles>. Un perfil de Maven es configuración que solo se activa si la pides con -P. El perfil bd activa el plugin failsafe, que ejecuta los tests de base de datos (*IT). Sin -Pbd esos tests no se ejecutan y el build no necesita el túnel.

Lo que quitamos a propósitoEl generador oficial (Spring Initializr) añadió seis piezas extra de Spring Modulith: observabilidad, integración con Actuator y un registro de eventos en base de datos. No las necesitamos, así que se quitaron. Revisar lo que genera una herramienta es parte del trabajo.

El paquete io.github.canaritel.mitusalud

En Java, los paquetes empiezan por un dominio que controlas escrito al revés (com.empresa…), para que dos proyectos nunca choquen. El proyecto no tiene dominio propio, y la convención para proyectos de GitHub es io.github.<usuario>.

Cada tipo de registro tiene sus propias clases en cada capa. A propósito no hay un controller ni un service "genérico" para todos los tipos: con dos tipos, la repetición es pequeña y cada clase se lee sola. Se valorará generalizar si la repetición llega a estorbar.

MitusaludApplication lleva @SpringBootApplication, que hace dos cosas: busca clases de Spring (@RestController, @Service…) en su paquete y en todos los que cuelgan de él, y configura automáticamente lo que encuentre en el pom.xml (base de datos, web…). Por eso todo el código vive por debajo de ese paquete.

Módulos (monolito modular). Es una sola aplicación, pero cada paquete directo (diario, comun, y en el futuro ingesta y analitica) es un módulo con fronteras: no usa las clases internas de otro módulo y es dueño de sus tablas. Si algún día un módulo necesita ser un servicio aparte, se puede extraer sin desenredar nada. Un test lo vigila (sección 8).

Capas dentro de cada módulo. Cada tipo de clase va en su carpeta y cada capa tiene un solo trabajo:

CapaTrabajoLo que nunca hace

serviceReglas de negocio y transacciones.Saber nada de HTTP.

dtoDefinir qué entra y qué sale por la API.Guardarse en la base de datos.

5. Recorrido de una petición

Qué pasa, paso a paso, cuando registras un peso:

POST http://localhost:8080/api/v1/pesos
Content-Type: application/json

{"observadoEn": "2026-09-26T08:30:00+02:00", "kilos": 72.35}
  1. Llega al servidor web. Tomcat, integrado en la app, recibe la petición y la atiende en un virtual thread (hilo ligero de Java 21), activado con spring.threads.virtual.enabled=true.
  2. Spring busca quién la atiende. Mira la ruta y el método: @RequestMapping("/api/v1/pesos") + @PostMapping → PesoController.registrar.
  3. JSON → Java. Jackson convierte el JSON en un PesoEntrada. Si el JSON está roto o kilos es texto, se corta aquí con un 400.
  4. Validación. @Valid aplica las reglas del record: momento obligatorio, con zona horaria y no futuro; kilos positivos, menores de 500 y con 2 decimales como máximo (72.355 se rechaza, no se redondea). Si falla, ManejadorErroresApi responde 400 indicando qué campos fallan (sección 7).
  5. El controller delega. Llama a pesoService.registrar(entrada). No hace nada más.
  6. Transacción. @Transactional abre una transacción: o se guarda todo o nada.
  7. Se crea la entidad y se guarda. new Peso(observadoEn.toInstant(), kilos) y pesoRepository.save(...). Hibernate genera el id (UUID v7) y hace dos INSERT: uno en observation y otro en peso. PostgreSQL comprueba sus CHECK; si falla el segundo, la transacción deshace también el primero.
  8. Java → JSON. PesoSalida.de(peso) convierte la entidad en el record de salida; Jackson lo pasa a JSON y @ResponseStatus(CREATED) pone el código 201.
HTTP 201 Created
{"id": "01a0df72-5b26-7787-8ed3-6fc10ca94f1b", "observadoEn": "2026-09-26T06:30:00Z", "kilos": 72.35}

La hora vuelve en UTC (Z): 08:30 en +02:00 es el mismo instante que 06:30 en UTC. La base de datos guarda el instante, no la zona con la que se envió; mostrarlo en hora local es trabajo de la interfaz.

¿Por qué dos records y no devolver la entidad?

  • PesoEntrada no tiene id. El cliente no puede inventarse ni sobrescribir un id, porque ese campo sencillamente no existe en lo que envía. Es seguridad, no burocracia. Lo mismo servirá para el propietario cuando llegue el login.
  • PesoSalida separa la API de la tabla. Si mañana la tabla gana una columna interna, la API no la expone por accidente ni se rompe sin que te enteres.
// Así de pequeños son:
public record PesoEntrada(@NotNull @PastOrPresent OffsetDateTime observadoEn, @NotNull @Positive ... BigDecimal kilos) {}
public record PesoSalida(UUID id, Instant observadoEn, BigDecimal kilos) {
    public static PesoSalida de(Peso peso) { ... }  // conversión a mano
}

El agua sigue el mismo recorrido

POST /api/v1/agua con {"observadoEn": "2026-09-26T10:00:00+02:00", "mililitros": 250} pasa por las mismas capas con sus propias clases (AguaController, AguaService…). La ruta va en singular porque el agua no se cuenta en unidades. Los mililitros son enteros entre 1 y 5000 por registro.

Una trampa de JacksonPor defecto, Jackson convierte un decimal en un entero truncándolo sin avisar: "mililitros": 250.5 se guardaría como 250. Lo descubrió un test al añadir el agua. Se desactiva en application.properties con spring.jackson.deserialization.accept-float-as-int=false, y ahora 250.5 responde 400.

La lista: GET /api/v1/pesos

El controller llama a pesoService.listar(), que abre una transacción de solo lectura y llama a findAllByOrderByObservadoEnDescIdDesc(). Ese método no tiene código: Spring Data lee su nombre y genera la consulta, y Hibernate une las tablas peso y observation y ordena por observed_at DESC, id DESC. El id solo desempata registros del mismo instante, siempre en el mismo orden. Cada entidad se convierte en PesoSalida y se devuelve la lista.

Dos ajustes de application.properties que afectan al recorrido

  • spring.jpa.open-in-view=false: por defecto Spring mantiene abierta la conexión a la base de datos mientras genera la respuesta, lo que permite consultas "escondidas" fuera del service. Se desactiva para que todo acceso a datos ocurra en el service, a la vista.
  • spring.jpa.hibernate.ddl-auto=validate: Hibernate no crea ni cambia tablas; solo comprueba que las entidades coinciden con ellas. Las tablas son cosa de Flyway.

6. Base de datos

PostgreSQL en Docker, en un servidor

PostgreSQL corre en un servidor Linux dentro de un contenedor Docker propio del proyecto. Así no se instala nada en el PC de desarrollo y no se mezcla con bases de datos de otros proyectos.

services:
  postgres:
    image: postgres:17                  # versión Debian: ordena bien acentos y ñ
    container_name: mitusalud-postgres
    restart: unless-stopped             # arranca sola si el servidor se reinicia
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Falta ...}  # sin contraseña, no arranca
    ports:
      - "127.0.0.1:5433:5432"           # solo accesible desde el propio servidor
    volumes:
      - postgres-datos:/var/lib/postgresql/data  # los datos sobreviven al contenedor
    healthcheck: ...                    # Docker comprueba que acepta conexiones

La línea de ports se lee "puerto del servidor : puerto del contenedor". El 127.0.0.1 delante hace que nadie de la red pueda conectarse directamente, y el 5433 evita chocar con otros PostgreSQL que usen el 5432.

El túnel SSH

Si la base de datos solo escucha dentro del servidor, ¿cómo llega el backend desde tu PC? Con un túnel:

ssh -N -L 5433:localhost:5433 usuario@servidor
ParteSignificado
-L 5433:localhost:5433"Lo que llegue al puerto 5433 de mi PC, envíalo por SSH y entrégalo en localhost:5433, visto desde el servidor".
-NNo ejecutar ningún comando en el servidor; solo mantener el túnel.

Con el túnel abierto, para el backend la base de datos está en localhost:5433, como si estuviera en tu PC. Ventajas: el puerto no está abierto a la red y la contraseña viaja cifrada dentro de SSH.

Flyway: las tablas se versionan como el código

Las tablas no se crean a mano ni las crea Hibernate. Se escriben scripts SQL numerados en src/main/resources/db/migration/:

V1__crear_tabla_peso.sql          ← el esqueleto inicial
V2__peso_como_observacion.sql     ← el modelo definitivo del peso
V3__agua.sql                      ← segundo tipo de registro
V4__...sql                        ← el siguiente cambio

Al arrancar, Flyway mira la tabla flyway_schema_history (la crea él) para saber qué scripts ya aplicó, y ejecuta solo los nuevos, en orden. Así cualquier instalación, hoy o dentro de un año, acaba con las mismas tablas.

Regla de oroNunca se modifica un script ya aplicado: Flyway guarda su huella y se negaría a arrancar. Cualquier cambio va en un script nuevo. Por eso V1 sigue existiendo aunque su tabla ya no: V2 la borra y crea las nuevas. Los datos de V1 eran inventados y se descartaron en vez de migrarse.

Conceptos básicos de las tablas

Una tabla no solo guarda datos: también declara reglas (restricciones, en inglés constraints) que PostgreSQL hace cumplir siempre, venga el dato de donde venga. Si una fila incumple una regla, PostgreSQL la rechaza y no guarda nada. Estas son las que usa mitusalud:

ConceptoQué esEjemplo en mitusalud
PRIMARY KEY
(clave primaria)		La columna que identifica cada fila. Es única y nunca puede estar vacía.observation.id
NOT NULLLa columna es obligatoria: no admite "vacío" (NULL).observed_at: todo registro tiene un momento
DEFAULTValor que PostgreSQL pone si el INSERT no envía esa columna.peso.type vale 'weight'
CHECKUna condición que cada fila debe cumplir.kilos > 0 AND kilos < 500
UNIQUENo puede haber dos filas con el mismo valor, o con la misma combinación si son varias columnas.UNIQUE (id, type) en observation
FOREIGN KEY
(clave foránea)		"Este valor tiene que existir en otra tabla". Enlaza tablas y evita referencias a filas que no existen.peso.observation_id debe ser el id de una observación
Clave foránea compuestaLo mismo, pero con varias columnas a la vez: la combinación tiene que existir en la otra tabla. La otra tabla necesita un UNIQUE (o clave primaria) sobre esas columnas.(observation_id, type) → (id, type): un peso solo puede colgar de una observación de tipo weight
ON DELETE CASCADEQué pasa al borrar la fila referenciada: con CASCADE, se borran también las que la apuntan.Borrar una observación borra su fila de peso
ÍndiceEstructura que acelera las búsquedas, como el índice de un libro. PRIMARY KEY y UNIQUE crean uno automáticamente.Buscar un peso por su id no recorre toda la tabla

Así responde PostgreSQL cuando se rompe cada regla (mensajes reales de PostgreSQL 17 con estas tablas). Aprender a leerlos ahorra mucho tiempo: siempre dicen qué tabla y qué restricción.

-- NOT NULL: falta el momento
ERROR: null value in column "observed_at" of relation "observation" violates not-null constraint

-- PRIMARY KEY: dos observaciones con el mismo id
ERROR: duplicate key value violates unique constraint "observation_pkey"

-- CHECK: un tipo que no está en la lista
ERROR: new row for relation "observation" violates check constraint "observation_type_check"

-- CHECK: 600 kg
ERROR: new row for relation "peso" violates check constraint "peso_kilos_check"

-- FOREIGN KEY: un peso que apunta a una observación que no existe (o de otro tipo)
ERROR: insert or update on table "peso" violates foreign key constraint "peso_observation_id_type_fkey"

Los nombres como peso_kilos_check los inventa PostgreSQL: tabla + columna + tipo de regla. Por eso un test puede comprobar que un fallo viene de una regla concreta (sección 8).

Las tablas observation y peso

Cada registro del diario tiene dos partes: lo común a cualquier tipo (cuándo ocurrió, qué tipo es) en observation, y lo propio de su tipo en una tabla de detalle. Hoy solo existe el peso; el agua o la energía tendrán su propia tabla de detalle.

CREATE TABLE observation (
    id          UUID        PRIMARY KEY,
    type        TEXT        NOT NULL CHECK (type IN ('weight')),
    observed_at TIMESTAMPTZ NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (id, type)
);

CREATE TABLE peso (
    observation_id UUID          PRIMARY KEY,
    type           TEXT          NOT NULL DEFAULT 'weight' CHECK (type = 'weight'),
    kilos          NUMERIC(5, 2) NOT NULL CHECK (kilos > 0 AND kilos < 500),
    FOREIGN KEY (observation_id, type) REFERENCES observation (id, type) ON DELETE CASCADE
);
ElecciónPor qué
UUID (versión 7)Identificadores independientes de cada instalación. Los genera la aplicación antes de insertar. Empiezan por la hora de generación: no son secretos, y el orden cronológico lo da observed_at, no el id.
type + CHECKQué tipo de registro es. La lista de tipos permitidos crece con cada migración.
UNIQUE (id, type) + FK (observation_id, type)Junto con el type fijo de peso, impiden colgar un peso de una observación de otro tipo.
DEFAULT 'weight' en peso.typeLa aplicación no envía esa columna: la rellena PostgreSQL.
ON DELETE CASCADEBorrar una observación borra su detalle.
NUMERIC(5,2) y BigDecimal en JavaDecimales exactos. Con double, 0.1 + 0.2 no da exactamente 0.3.
CHECK de los kilosLa propia base de datos rechaza valores absurdos, aunque el backend tuviera un fallo.
TIMESTAMPTZGuarda un instante exacto en la línea de tiempo. Ojo: no guarda la zona horaria original (por ejemplo Europe/Madrid), solo el instante.
Lo que PostgreSQL no puede impedirQue exista una fila en observation sin su detalle. Eso lo garantiza la aplicación guardando las dos filas en la misma transacción, y lo comprueba un test (PesoTransaccionIT, sección 8).

Segundo tipo: la tabla agua (V3)

Añadir un tipo de registro son dos cosas: permitir el tipo nuevo en observation y crear su tabla de detalle con el mismo patrón.

-- Un CHECK no se puede editar: se borra y se vuelve a crear con la lista ampliada.
ALTER TABLE observation DROP CONSTRAINT observation_type_check;
ALTER TABLE observation ADD CONSTRAINT observation_type_check CHECK (type IN ('weight', 'water'));

CREATE TABLE agua (
    observation_id UUID    PRIMARY KEY,
    type           TEXT    NOT NULL DEFAULT 'water' CHECK (type = 'water'),
    mililitros     INTEGER NOT NULL CHECK (mililitros > 0 AND mililitros <= 5000),
    FOREIGN KEY (observation_id, type) REFERENCES observation (id, type) ON DELETE CASCADE
);

Ese ALTER va en V3, no en V2: V2 ya estaba aplicada y una migración aplicada nunca se modifica. El nombre observation_type_check lo puso PostgreSQL al crear la tabla en V2 (tabla + columna + tipo de regla). Los 5000 ml son por registro, no por día.

Herencia JOINED: dos tablas, una clase Java

En Java, un Peso es una Observacion: Peso extends Observacion. JPA traduce esa herencia a tablas con la estrategia JOINED: la clase padre tiene su tabla y cada subclase la suya, unidas por la clave.

@Entity @Table(name = "observation")
@Inheritance(strategy = InheritanceType.JOINED)   // cada subclase, su tabla de detalle
@DiscriminatorColumn(name = "type")               // Hibernate escribe el tipo aquí
public abstract class Observacion { UUID id; Instant observadoEn; Instant creadoEn; }

@Entity @Table(name = "peso")
@DiscriminatorValue("weight")                     // el valor de type para los pesos
@PrimaryKeyJoinColumn(name = "observation_id")    // la clave de peso es la de su observación
public class Peso extends Observacion { BigDecimal kilos; }

@Entity @Table(name = "agua") @DiscriminatorValue("water") @PrimaryKeyJoinColumn(name = "observation_id")
public class Agua extends Observacion { Integer mililitros; }

Esto es lo que Hibernate envía a PostgreSQL al guardar un peso (sacado del log real):

insert into observation (created_at, observed_at, type, id) values (?, ?, 'weight', ?)
insert into peso (kilos, observation_id) values (?, ?)

Al leer, hace un JOIN de las dos tablas y devuelve un Peso completo. Observacion es abstract: en el código no puede existir una observación sin tipo.

Cómo encuentra el backend la contraseña

spring.config.import=optional:file:../.env[.properties]
spring.datasource.password=${POSTGRES_PASSWORD}

La primera línea le dice a Spring que lea el .env de la raíz del proyecto como si fuera un archivo de propiedades. La ruta ../ es relativa a la carpeta desde la que arrancas, por eso el backend se arranca siempre desde backend/. optional: evita un error si el archivo no existe, por ejemplo en un servidor donde la contraseña llegue como variable de entorno.

Cambiar la contraseña más adelante

La imagen de PostgreSQL solo usa POSTGRES_PASSWORD la primera vez, cuando el volumen de datos está vacío y crea la base de datos. Después la ignora. Si solo cambias los .env, la base de datos sigue con la contraseña antigua y el backend deja de conectar. El orden correcto:

# 1. En el servidor, cambia la contraseña dentro de PostgreSQL
docker exec -it mitusalud-postgres psql -U mitusalud -c "ALTER USER mitusalud PASSWORD 'nueva'"

# 2. Pon la nueva en los dos .env (servidor y PC) y reinicia el backend

7. Errores e idiomas

ProblemDetail: un formato de error estándar

Todos los errores de la API salen con el mismo formato JSON, definido por el estándar RFC 9457. El frontend siempre sabe dónde mirar:

HTTP 400
{
  "title": "Petición no válida",
  "status": 400,
  "detail": "Hay campos con valores no válidos.",
  "instance": "/api/v1/pesos",
  "errores": {
    "observadoEn": "debe ser una fecha en el pasado o en el presente",
    "kilos": "debe ser mayor que 0"
  }
}

Lo hace comun/ManejadorErroresApi. Hereda de ResponseEntityExceptionHandler, la clase de Spring que ya convierte los errores habituales en ProblemDetail, y solo cambia el caso de la validación para añadir errores. Los campos salen en orden alfabético para que la misma petición dé siempre la misma respuesta.

Español e inglés

El navegador envía en cada petición la cabecera Accept-Language con sus idiomas preferidos. comun/ConfiguracionIdioma admite dos idiomas y elige el mejor:

Accept-LanguageRespuesta
(ninguna)Español

fr u otro no admitidoEspañol (sin mezclar idiomas)
de,en;q=0.8Inglés: es el mejor de los que admitimos

Los textos no están escritos en el código. Viven en messages.properties (español) y messages_en.properties (inglés) con las mismas claves. Los mensajes de validación ("debe ser mayor que 0") vienen ya traducidos en Hibernate Validator. Añadir un idioma es crear otro archivo de textos y sumarlo a la lista de ConfiguracionIdioma.

Proteger la base de datos en los tests: @UsaBaseDeDatosDeTest

Los tests con base de datos deben tocar solo mitusalud_test, nunca tu base de desarrollo ni la instalación real de nadie. Todos llevan la anotación @UsaBaseDeDatosDeTest, que agrupa dos protecciones para que ningún test pueda llevar una y olvidar la otra:

  1. @TestPropertySource carga bd-test.properties. Spring decide qué configuración gana por un orden de prioridad, y en ese orden una variable de entorno como SPRING_DATASOURCE_URL gana a los archivos application*.properties. En cambio, @TestPropertySource está por encima de las variables de entorno, así que nada externo puede redirigir los tests.
  2. GuardiaBaseDeTest, antes de Flyway. Justo antes de migrar, pregunta a PostgreSQL a qué base están conectadas las dos conexiones: la de Flyway (crea las tablas) y la de JPA (la que usan los tests). Spring permite que sean distintas con spring.flyway.url, así que comprobar solo una dejaría un hueco. Si alguna no es mitusalud_test, detiene los tests con el mensaje "Los tests solo pueden usar la base 'mitusalud_test', pero JPA está conectado a 'mitusalud'. No se ha modificado nada." Protege de despistes como editar mal el archivo.

Una anotación que agrupa otras se llama meta-anotación: Spring lee las anotaciones de dentro como si estuvieran puestas en el test.

Tests del repository: PesoRepositoryIT

Usan @DataJpaTest, que arranca solo JPA, Flyway y los repositories, contra un PostgreSQL real.

  • Por defecto @DataJpaTest cambiaría la base de datos por una en memoria. @AutoConfigureTestDatabase(replace = NONE) lo impide: una base de datos distinta podría dar por bueno algo que en PostgreSQL falla.
  • Cada test corre dentro de una transacción que se deshace al terminar: la base de test queda siempre vacía.
  • Al arrancar, Flyway aplica las migraciones y Hibernate valida la entidad contra la tabla. Si un script o una entidad tienen un error, fallan todos.

La trampa de la caché de primer nivelHibernate guarda en memoria las entidades que ya conoce dentro de una transacción. Si guardas un objeto y justo después lo buscas por id, Hibernate te devuelve el mismo objeto de memoria sin preguntar a la base de datos, y el test pasaría aunque PostgreSQL hubiera guardado otra cosa. Por eso el test de decimales llama a entityManager.clear() antes de leer: obliga a hacer un SELECT real. Esta trampa la detectó una revisión mirando el log de SQL: el test solo hacía un INSERT.

La transacción de verdad: PesoTransaccionIT

Comprueba la regla que PostgreSQL no puede imponer: si falla el detalle, tampoco queda la observación. Llama al service con 600 kg (sin pasar por la validación del controller), el CHECK de peso lo rechaza y la transacción se deshace. El test exige que el fallo venga de ese CHECK (SQLState 23514, restricción peso_kilos_check): si fallara antes por otro motivo, no demostraría nada. Después cuenta las filas de observation y peso con SQL directo (JdbcTemplate).

A propósito, este test no lleva @Transactional: si lo llevara, el rollback lo haría el propio test y no demostraría nada sobre la transacción del service. Se cuenta con SQL directo, no con las entidades, para que no se escape una fila de observation sin detalle.

Comprobar que un test puede fallarUn test que pasa no demuestra nada si también pasaría con el código roto. Por eso, tras escribir estos dos tests, se rompió el código a propósito y se comprobó que fallan: desempatar por id ascendente hace fallar el test del orden, y un NullPointerException antes del INSERT hace fallar el del rollback. Después se restauró el código.

Test de punta a punta: PesoApiIT

Usa @SpringBootTest, que arranca la aplicación completa, sin nada simulado: controller → service → repository → PostgreSQL. Registra un peso por la API con hora en +02:00, comprueba que la respuesta devuelve el mismo instante en UTC, guarda el id devuelto y comprueba que la lista contiene ese mismo registro con su momento y su peso. Buscar "cualquier peso de 71.8 kg" podría aprobar gracias a otro registro. Los tests de cada capa por separado no ven si las capas encajan entre sí; este sí.

@Transactional deshace todo al terminar. Funciona porque MockMvc ejecuta la petición en el mismo hilo y la misma transacción que el test.

CompruebaNo comprueba
Que controller, service, repository y PostgreSQL encajan: rutas, JSON, validación, transacción, SQL real.Una conexión HTTP real: MockMvc simula la petición sin red.
Que el dato sobreviva entre transacciones separadas: todo ocurre en una sola y se deshace.

Para cubrir lo de la derecha haría falta arrancar el servidor de verdad (@SpringBootTest(webEnvironment = RANDOM_PORT)) y usar un cliente HTTP real. Se añadirá cuando aporte algo; ahora sería sobredimensionar.

9. Integración continua (GitHub Actions)

En cada push a main y en cada pull request, GitHub compila el backend y ejecuta todos los tests en una máquina limpia, incluidos los de base de datos. Si algo falla, el commit aparece con una ✗ roja y GitHub avisa por email. El resultado se ve en el badge del README.

Qué es CI (y qué no)

CI (Continuous Integration, integración continua) es una práctica: integrar los cambios en la rama principal a menudo y verificar cada uno automáticamente (compilar y pasar los tests). Así un error se detecta en minutos, cuando aún recuerdas qué cambiaste, y no semanas después.

No hay que confundirlo con CD (Continuous Delivery / Deployment): preparar o desplegar automáticamente cada versión que pasa la CI. mitusalud tiene CI, no CD: nada se despliega solo.

GitHub Actions es la herramienta de GitHub que ejecuta esa verificación. Su vocabulario, aplicado a nuestro ci.yml:

TérminoQué esEn mitusalud
WorkflowUn proceso automático, definido en un archivo YAML dentro de .github/workflows/.ci.yml (nombre: CI)
Trigger (on:)Qué lo dispara.Push a main y pull requests
JobUn bloque de trabajo que corre en una máquina.backend
RunnerLa máquina (virtual, limpia) que GitHub presta para ejecutar el job.ubuntu-latest
StepCada paso del job, en orden.Descargar código, instalar Java, ejecutar tests
ActionUn paso reutilizable publicado por otros.actions/checkout, actions/setup-java
Service containerUn contenedor auxiliar que vive mientras dura el job.El PostgreSQL desechable

Qué se gana

  • No depende de acordarse: los tests se ejecutan solos.
  • Máquina limpia: detecta el "en mi máquina funciona", como un archivo sin subir, un permiso de mvnw o los saltos de línea.
  • Sin túnel ni servidor: los tests de base de datos usan un PostgreSQL que GitHub crea y destruye en cada ejecución.
  • Contribuciones probadas: en un repo público, los cambios que proponga otra persona se prueban antes de aceptarlos.

El archivo .github/workflows/ci.yml

GitHub busca los workflows en esa carpeta exacta. Las partes clave:

on:
  push:
    branches: [main]      # cuándo se ejecuta
  pull_request:

permissions:
  contents: read          # permisos mínimos: solo leer el código

services:
  postgres:               # "service container": PostgreSQL desechable junto al job
    image: postgres:17
    env:
      POSTGRES_DB: mitusalud_test
      POSTGRES_PASSWORD: ci   # desechable: la base solo existe durante la prueba
    ports:
      - 5433:5432         # mismo puerto que el túnel en desarrollo

steps:
  - uses: actions/checkout@v7       # descarga el código
  - uses: actions/setup-java@v6     # instala Java 21 y guarda la caché de Maven
  - run: ./mvnw -B verify -Pbd      # compila y pasa todos los tests

El PostgreSQL de GitHub imita a propósito el entorno de desarrollo: se llama mitusalud_test, escucha en el puerto 5433 y usa el usuario mitusalud. Por eso los tests funcionan tal cual, sin cambiar código ni configuración. Como allí no existe .env, la contraseña llega como variable de entorno (POSTGRES_PASSWORD), que Spring lee igual. El guardia de la base de datos sigue protegiendo exactamente igual.

¿Por qué no Testcontainers?Testcontainers arranca PostgreSQL desde el código de los tests y añade una dependencia al proyecto. GitHub Actions ya ofrece los service containers con unas líneas de configuración, así que en CI no hace falta. Testcontainers sigue como propuesta por si algún día hay Docker en el equipo de desarrollo.
Idioma de la máquinaLos servidores de GitHub están en inglés y tu PC quizá en español. Los tests esperan mensajes en español y pasan igual, porque el idioma lo decide la petición (ConfiguracionIdioma), no la máquina. Se comprobó antes de subir el workflow ejecutando los tests con la JVM en inglés.

-B (batch mode) le dice a Maven que no hay nadie delante: sin colores ni barras de progreso, así los logs de GitHub son legibles.

Usar GitHub Actions en el día a día

  1. Haz push como siempre. No hay que lanzar nada: el workflow arranca solo en uno o dos segundos.
  2. Mira el resultado. En GitHub, junto a cada commit aparece un punto amarillo (en marcha), un ✓ verde o una ✗ roja. También en la pestaña Actions del repo y en el badge del README. Si falla, GitHub te avisa por email.
  3. Si falla, lee el log. Actions → la ejecución con la ✗ → el job → el paso marcado en rojo. Busca FAIL, ERROR o Tests run:: el log de Maven dice qué test falló y por qué.
  4. Reprodúcelo en tu PC. El workflow ejecuta exactamente ./mvnw -B verify -Pbd: con el túnel abierto, ese mismo comando reproduce el fallo en local, donde es más fácil depurarlo.
  5. Relanzar. El botón Re-run jobs repite la ejecución sin hacer push. Úsalo solo si el fallo fue algo pasajero (por ejemplo, la red); si un test falla de verdad, relanzar no lo arregla.

Lo mismo desde la terminal, con la herramienta gh de GitHub:

gh run list                      # últimas ejecuciones y su resultado
gh run watch                     # sigue en directo la ejecución en marcha
gh run view --log-failed         # muestra solo el log de los pasos que fallaron
gh run rerun <id>                # relanza una ejecución

En un pull request, el resultado aparece como un check antes de aceptar los cambios: así se sabe si una contribución rompe algo sin tener que probarla a mano.

12. Glosario

API REST
Forma de comunicar programas por HTTP usando rutas (/api/v1/pesos) y métodos (GET para leer, POST para crear…).
Endpoint
Una ruta concreta de la API con su método, por ejemplo POST /api/v1/pesos.
JSON
Formato de texto para intercambiar datos: {"kilos": 72.35}.
Entidad
Clase Java que representa una fila de una tabla (Peso).
DTO
Data Transfer Object: objeto que solo transporta datos entre la API y el código (PesoEntrada, PesoSalida).
Record
Clase de Java pensada para transportar datos: en una línea define campos, constructor, getters, equals y toString.
ORM / JPA / Hibernate
Un ORM traduce entre objetos Java y tablas. JPA es el estándar de Java para hacerlo; Hibernate es la implementación que usa Spring.
Spring Data
Genera los repositories a partir de interfaces y del nombre de sus métodos.
Transacción
Grupo de operaciones en la base de datos que se aplican todas o ninguna.
Migración
Script que cambia la estructura de la base de datos de forma controlada y versionada (Flyway).
CRUD
Create, Read, Update, Delete: las cuatro operaciones básicas sobre datos.
Contenedor / Docker
Un contenedor empaqueta un programa con todo lo que necesita para funcionar igual en cualquier máquina. Docker es la herramienta que los ejecuta.
Volumen
Espacio de disco que Docker guarda fuera del contenedor, para que los datos sobrevivan aunque se borre.
Túnel SSH
Conexión cifrada que lleva el tráfico de un puerto de tu PC a un puerto del servidor.
Starter
Dependencia de Spring Boot que agrupa todo lo necesario para una tarea.
Monolito modular
Una sola aplicación dividida en módulos con fronteras claras, que podrían separarse en servicios más adelante.
Arquitectura hexagonal
Diseño en el que las reglas de negocio no dependen de la base de datos ni de la web: se conectan con ellas mediante interfaces ("puertos") y sus implementaciones ("adaptadores").
Virtual threads
Hilos ligeros de Java 21: permiten atender muchas peticiones a la vez con código normal.
ProblemDetail
Formato estándar (RFC 9457) para devolver errores de una API en JSON.
i18n
Internacionalización: preparar la app para varios idiomas sacando los textos del código.
LTS
Long Term Support: versión con soporte y parches durante años. Java 21 lo es.
OpenAPI / Swagger UI
OpenAPI es el estándar para describir una API; Swagger UI es la página web que lee esa descripción y deja probar la API.
Healthcheck
Comprobación automática de si un servicio funciona (/actuator/health, el healthcheck de Docker).
Clave primaria (PRIMARY KEY)
Columna (o columnas) que identifica cada fila de una tabla: única y obligatoria.
Clave foránea (FOREIGN KEY)
Columna cuyo valor debe existir en otra tabla. Enlaza tablas y evita referencias rotas.
Restricción (constraint)
Regla declarada en una tabla que PostgreSQL hace cumplir siempre: NOT NULL, CHECK, UNIQUE, claves primarias y foráneas.
Índice
Estructura que acelera las búsquedas en una tabla. Las claves primarias y los UNIQUE crean uno automáticamente.
CI (integración continua)
Verificar automáticamente cada cambio (compilar y pasar tests) al integrarlo en la rama principal.
CD (entrega o despliegue continuo)
Preparar o desplegar automáticamente cada versión que pasa la CI. mitusalud no lo tiene.
Workflow, job, step, runner
En GitHub Actions: el proceso automático (archivo YAML), sus bloques de trabajo, los pasos de cada bloque y la máquina que los ejecuta.
