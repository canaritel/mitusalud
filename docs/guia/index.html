Actualizada el 26/09/2026 · Estado: backend con registro de peso y tests

1. Qué es mitusalud y cómo encaja todo

mitusalud es un diario personal de salud: alimentación, sueño, actividad, gimnasio, medicación, analíticas… Cada persona lo instala en su propio servidor y guarda allí sus datos. No es un servicio compartido: cada instalación tiene un único propietario.

Hoy existe la primera pieza que funciona de punta a punta: registrar tu peso y verlo en una lista. Todo lo demás crecerá sobre ese esqueleto.

Un esqueleto provisional, a propósitoLa tabla peso es deliberadamente simple: sirve para comprobar que toda la cadena funciona (API, validación, errores, Flyway, PostgreSQL). El modelo definitivo del backlog, donde el peso es una "observación" con propietario, auditoría y revisiones, se decidirá antes de añadir un segundo tipo de registro. Así no se construye diez veces lo mismo.

La base de datos vive en un servidor con Docker, así en tu PC no instalas ni Docker ni PostgreSQL. Los dos se hablan a través de un túnel SSH (lo explica la sección 6).

2. Principios

Estas reglas explican casi todas las decisiones del proyecto. Cuando dudes de por qué algo es así, empieza por aquí.

PrincipioQué significa en la práctica
No sobredimensionarUna tecnología entra cuando hay una necesidad real, no "por si acaso". Cada pieza extra hay que instalarla, configurarla, entenderla y protegerla.
Sencillo antes que fácil"Fácil" es lo que parece rápido hoy (un generador mágico, una librería que lo hace todo). "Sencillo" es lo que tiene pocas piezas y poco enredadas. Elegimos lo sencillo aunque cueste un poco más al principio.
Comprensible para un juniorEl código lleva comentarios que explican por qué, no lo que ya se lee en el código.
DTOs mínimosNada de cinco clases por concepto. Una entidad y, como mucho, un record de entrada y otro de salida, de una línea cada uno. Conversión a mano, sin librerías de mapeo.
Paso a pasoPrimero un esqueleto mínimo que funciona de punta a punta; después crece con cada necesidad.

La lista completa de tecnologías, con su estado (aprobada, propuesta o descartada), está en docs/STACK.md.

Maven: qué es

Maven hace dos trabajos:

  • Descarga las librerías que declara el pom.xml (Spring, el driver de PostgreSQL…), y las librerías que esas librerías necesitan. Las guarda en ~/.m2/repository para no descargarlas otra vez.
  • Construye el proyecto en fases siempre en el mismo orden: compile → test → package (crea el .jar) → verify. Si pides una fase, se ejecutan también todas las anteriores. Por eso ./mvnw verify compila y pasa los tests.

.mvn/, mvnw y mvnw.cmd: el Maven Wrapper

Es la respuesta a "¿por qué no tengo que instalar Maven?".

  • mvnw y mvnw.cmd son dos scripts pequeños (uno para Linux/macOS/Git Bash, otro para Windows) que hacen lo mismo que el comando mvn.
  • La primera vez leen .mvn/wrapper/maven-wrapper.properties, descargan exactamente la versión de Maven que dice ahí (ahora la 3.9.16) y la guardan en ~/.m2/wrapper. Las siguientes veces la reutilizan.
  • Resultado: cualquiera que clone el repo usa la misma versión de Maven, sin instalar nada. Se acabó el "en mi máquina compila".

La carpeta empieza por punto (.mvn) porque en Linux eso la oculta: es configuración de herramientas, no código que tengas que tocar.

.gitattributes: por qué importan los saltos de línea

Windows termina cada línea con dos caracteres invisibles (CRLF); Linux, con uno (LF). Git puede convertirlos al descargar, y eso rompe mvnw en Linux: la primera línea #!/bin/sh pasaría a terminar en un carácter extra y Linux respondería bad interpreter.

/mvnw  text eol=lf     # mvnw siempre con saltos de Linux
*.cmd  text eol=crlf   # los .cmd siempre con saltos de Windows

Además, mvnw está marcado en git como ejecutable, para que en Linux funcione ./mvnw sin hacer chmod +x.

pom.xml: dependencia por dependencia

El pom.xml hereda de spring-boot-starter-parent. Ese "padre" fija versiones compatibles entre sí de cientos de librerías; por eso casi ninguna dependencia lleva número de versión. Un starter es un paquete que agrupa todo lo necesario para una tarea (por ejemplo, starter-webmvc trae el servidor web, Jackson para JSON, etc.).

Al final del pom.xml, spring-modulith-bom fija la versión de Spring Modulith (como hace el padre con Spring) y spring-boot-maven-plugin añade el comando spring-boot:run y empaqueta la app en un único .jar ejecutable.

Justo antes de <build> está el bloque <profiles>. Un perfil de Maven es configuración que solo se activa si la pides con -P. El perfil bd activa el plugin failsafe, que ejecuta los tests de base de datos (*IT). Sin -Pbd esos tests no se ejecutan y el build no necesita el túnel.

Lo que quitamos a propósitoEl generador oficial (Spring Initializr) añadió seis piezas extra de Spring Modulith: observabilidad, integración con Actuator y un registro de eventos en base de datos. No las necesitamos, así que se quitaron. Revisar lo que genera una herramienta es parte del trabajo.

El paquete io.github.canaritel.mitusalud

En Java, los paquetes empiezan por un dominio que controlas escrito al revés (com.empresa…), para que dos proyectos nunca choquen. El proyecto no tiene dominio propio, y la convención para proyectos de GitHub es io.github.<usuario>.

MitusaludApplication lleva @SpringBootApplication, que hace dos cosas: busca clases de Spring (@RestController, @Service…) en su paquete y en todos los que cuelgan de él, y configura automáticamente lo que encuentre en el pom.xml (base de datos, web…). Por eso todo el código vive por debajo de ese paquete.

Módulos (monolito modular). Es una sola aplicación, pero cada paquete directo (diario, comun, y en el futuro ingesta y analitica) es un módulo con fronteras: no usa las clases internas de otro módulo y es dueño de sus tablas. Si algún día un módulo necesita ser un servicio aparte, se puede extraer sin desenredar nada. Un test lo vigila (sección 8).

Capas dentro de cada módulo. Cada tipo de clase va en su carpeta y cada capa tiene un solo trabajo:

serviceReglas de negocio y transacciones.Saber nada de HTTP.
repositoryLeer y escribir en la tabla.Decidir nada.
entityRepresentar una fila de la tabla.Salir por la API.
dtoDefinir qué entra y qué sale por la API.Guardarse en la base de datos.

5. Recorrido de una petición

Qué pasa, paso a paso, cuando registras un peso:

POST http://localhost:8080/api/v1/pesos
Content-Type: application/json

{"fecha": "2026-09-26", "kilos": 72.35}
  1. Llega al servidor web. Tomcat, integrado en la app, recibe la petición y la atiende en un virtual thread (hilo ligero de Java 21), activado con spring.threads.virtual.enabled=true.
  2. Spring busca quién la atiende. Mira la ruta y el método: @RequestMapping("/api/v1/pesos") + @PostMapping → PesoController.registrar.
  3. JSON → Java. Jackson convierte el JSON en un PesoEntrada. Si el JSON está roto o kilos es texto, se corta aquí con un 400.
  4. Validación. @Valid aplica las reglas del record: fecha no nula y no futura, kilos positivos, menores de 500 y con 2 decimales como máximo. Si falla, ManejadorErroresApi responde 400 indicando qué campos fallan (sección 7).
  5. El controller delega. Llama a pesoService.registrar(entrada). No hace nada más.
  6. Transacción. @Transactional abre una transacción: o se guarda todo o nada.
  7. Se crea la entidad y se guarda. new Peso(fecha, kilos) y pesoRepository.save(...). Hibernate genera el INSERT; PostgreSQL asigna el id y comprueba su propio CHECK sobre los kilos.
  8. Java → JSON. PesoSalida.de(peso) convierte la entidad en el record de salida; Jackson lo pasa a JSON y @ResponseStatus(CREATED) pone el código 201.
HTTP 201 Created
{"id": 1, "fecha": "2026-09-26", "kilos": 72.35}

¿Por qué dos records y no devolver la entidad?

  • PesoEntrada no tiene id. El cliente no puede inventarse ni sobrescribir un id, porque ese campo sencillamente no existe en lo que envía. Es seguridad, no burocracia. Lo mismo servirá para el propietario cuando llegue el login.
  • PesoSalida separa la API de la tabla. Si mañana la tabla gana una columna interna, la API no la expone por accidente ni se rompe sin que te enteres.
// Así de pequeños son:
public record PesoEntrada(@NotNull @PastOrPresent LocalDate fecha, @NotNull @Positive ... BigDecimal kilos) {}
public record PesoSalida(Long id, LocalDate fecha, BigDecimal kilos) {
    public static PesoSalida de(Peso peso) { ... }  // conversión a mano
}

La lista: GET /api/v1/pesos

El controller llama a pesoService.listar(), que abre una transacción de solo lectura y llama a findAllByOrderByFechaDescIdDesc(). Ese método no tiene código: Spring Data lee su nombre y genera la consulta ORDER BY fecha DESC, id DESC. Cada entidad se convierte en PesoSalida y se devuelve la lista.

Dos ajustes de application.properties que afectan al recorrido

  • spring.jpa.open-in-view=false: por defecto Spring mantiene abierta la conexión a la base de datos mientras genera la respuesta, lo que permite consultas "escondidas" fuera del service. Se desactiva para que todo acceso a datos ocurra en el service, a la vista.
  • spring.jpa.hibernate.ddl-auto=validate: Hibernate no crea ni cambia tablas; solo comprueba que las entidades coinciden con ellas. Las tablas son cosa de Flyway.

6. Base de datos

PostgreSQL en Docker, en un servidor

PostgreSQL corre en un servidor Linux dentro de un contenedor Docker propio del proyecto. Así no se instala nada en el PC de desarrollo y no se mezcla con bases de datos de otros proyectos.

services:
  postgres:
    image: postgres:17                  # versión Debian: ordena bien acentos y ñ
    container_name: mitusalud-postgres
    restart: unless-stopped             # arranca sola si el servidor se reinicia
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Falta ...}  # sin contraseña, no arranca
    ports:
      - "127.0.0.1:5433:5432"           # solo accesible desde el propio servidor
    volumes:
      - postgres-datos:/var/lib/postgresql/data  # los datos sobreviven al contenedor
    healthcheck: ...                    # Docker comprueba que acepta conexiones

La línea de ports se lee "puerto del servidor : puerto del contenedor". El 127.0.0.1 delante hace que nadie de la red pueda conectarse directamente, y el 5433 evita chocar con otros PostgreSQL que usen el 5432.

El túnel SSH

Si la base de datos solo escucha dentro del servidor, ¿cómo llega el backend desde tu PC? Con un túnel:

ssh -N -L 5433:localhost:5433 usuario@servidor
ParteSignificado
-L 5433:localhost:5433"Lo que llegue al puerto 5433 de mi PC, envíalo por SSH y entrégalo en localhost:5433, visto desde el servidor".
-NNo ejecutar ningún comando en el servidor; solo mantener el túnel.

Con el túnel abierto, para el backend la base de datos está en localhost:5433, como si estuviera en tu PC. Ventajas: el puerto no está abierto a la red y la contraseña viaja cifrada dentro de SSH.

Flyway: las tablas se versionan como el código

Las tablas no se crean a mano ni las crea Hibernate. Se escriben scripts SQL numerados en src/main/resources/db/migration/:

V1__crear_tabla_peso.sql     ← ya existe
V2__...sql                   ← el siguiente cambio

Al arrancar, Flyway mira la tabla flyway_schema_history (la crea él) para saber qué scripts ya aplicó, y ejecuta solo los nuevos, en orden. Así cualquier instalación, hoy o dentro de un año, acaba con las mismas tablas.

Regla de oroNunca se modifica un script ya aplicado: Flyway guarda su huella y se negaría a arrancar. Cualquier cambio va en un script nuevo.

La tabla peso

CREATE TABLE peso (
    id        BIGINT        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    fecha     DATE          NOT NULL,
    kilos     NUMERIC(5, 2) NOT NULL CHECK (kilos > 0 AND kilos < 500),
    creado_en TIMESTAMPTZ   NOT NULL DEFAULT now()
);
ElecciónPor qué
GENERATED ALWAYS AS IDENTITYPostgreSQL genera el id. Es la forma estándar moderna (antes se usaba SERIAL).
NUMERIC(5,2) y BigDecimal en JavaDecimales exactos. Con double, 0.1 + 0.2 no da exactamente 0.3.
CHECKLa propia base de datos rechaza valores absurdos, aunque el backend tuviera un fallo.
TIMESTAMPTZMomento exacto con zona horaria. Evita líos con horarios de verano o cambios de país.
Varios pesos el mismo díaPermitido: puedes pesarte por la mañana y por la noche.

Cómo encuentra el backend la contraseña

spring.config.import=optional:file:../.env[.properties]
spring.datasource.password=${POSTGRES_PASSWORD}

La primera línea le dice a Spring que lea el .env de la raíz del proyecto como si fuera un archivo de propiedades. La ruta ../ es relativa a la carpeta desde la que arrancas, por eso el backend se arranca siempre desde backend/. optional: evita un error si el archivo no existe, por ejemplo en un servidor donde la contraseña llegue como variable de entorno.

Cambiar la contraseña más adelante

La imagen de PostgreSQL solo usa POSTGRES_PASSWORD la primera vez, cuando el volumen de datos está vacío y crea la base de datos. Después la ignora. Si solo cambias los .env, la base de datos sigue con la contraseña antigua y el backend deja de conectar. El orden correcto:

# 1. En el servidor, cambia la contraseña dentro de PostgreSQL
docker exec -it mitusalud-postgres psql -U mitusalud -c "ALTER USER mitusalud PASSWORD 'nueva'"

# 2. Pon la nueva en los dos .env (servidor y PC) y reinicia el backend

7. Errores e idiomas

ProblemDetail: un formato de error estándar

Todos los errores de la API salen con el mismo formato JSON, definido por el estándar RFC 9457. El frontend siempre sabe dónde mirar:

HTTP 400
{
  "title": "Petición no válida",
  "status": 400,
  "detail": "Hay campos con valores no válidos.",
  "instance": "/api/v1/pesos",
  "errores": {
    "fecha": "debe ser una fecha en el pasado o en el presente",
    "kilos": "debe ser mayor que 0"
  }
}

Lo hace comun/ManejadorErroresApi. Hereda de ResponseEntityExceptionHandler, la clase de Spring que ya convierte los errores habituales en ProblemDetail, y solo cambia el caso de la validación para añadir errores. Los campos salen en orden alfabético para que la misma petición dé siempre la misma respuesta.

Español e inglés

El navegador envía en cada petición la cabecera Accept-Language con sus idiomas preferidos. comun/ConfiguracionIdioma admite dos idiomas y elige el mejor:

Accept-LanguageRespuesta
(ninguna)Español
es, es-ESEspañol
en, en-GBInglés
fr u otro no admitidoEspañol (sin mezclar idiomas)
de,en;q=0.8Inglés: es el mejor de los que admitimos

Los textos no están escritos en el código. Viven en messages.properties (español) y messages_en.properties (inglés) con las mismas claves. Los mensajes de validación ("debe ser mayor que 0") vienen ya traducidos en Hibernate Validator. Añadir un idioma es crear otro archivo de textos y sumarlo a la lista de ConfiguracionIdioma.

8. Tests

Hay dos tipos de tests, y se ejecutan por separado:

ComandoQué ejecutaNecesita
./mvnw verifyTests normales (*Test): arquitectura y capa web.Nada. Segundos.
./mvnw verify -PbdLo anterior + tests de integración (*IT) contra PostgreSQL: repository y punta a punta.El túnel abierto.

La separación la hace Maven por el nombre de la clase: el plugin surefire ejecuta las *Test siempre, y el plugin failsafe ejecuta las *IT solo con el perfil bd (definido en el pom.xml). Así el día a día no depende del túnel.

Test de arquitectura: ModularidadTest

ApplicationModules.of(MitusaludApplication.class).verify();

Spring Modulith analiza el código compilado y falla si un módulo usa clases internas de otro o si dos módulos dependen el uno del otro en círculo.

Tests de la capa web: PesoControllerTest

Usan @WebMvcTest, que arranca solo lo necesario para HTTP: controller, validación, conversión JSON y manejador de errores. El service se sustituye por un mock con @MockitoBean: un objeto falso al que se le dice qué devolver. Así se prueba el controller aislado, en segundos y sin base de datos. MockMvc simula las peticiones HTTP sin arrancar un servidor real.

TestQué garantiza
Registrar un peso válidoResponde 201 con el registro.
Campos inválidosResponde 400 con los campos que fallan y no llama al service.
Falta la fechaEl error señala el campo que falta y solo ese.
Errores en inglés / idioma no admitidoEl idioma sigue a Accept-Language, con español por defecto.
JSON mal formadoResponde 400 con un mensaje claro.
ListarDevuelve lo que da el service, en el mismo orden.
Un detalle para fijarse@WebMvcTest no carga las clases @Configuration propias. Por eso el test importa ConfiguracionIdioma con @Import; sin ella, los idiomas no funcionarían en el test.

Proteger la base de datos en los tests: @UsaBaseDeDatosDeTest

Los tests con base de datos deben tocar solo mitusalud_test, nunca tu base de desarrollo ni la instalación real de nadie. Todos llevan la anotación @UsaBaseDeDatosDeTest, que agrupa dos protecciones para que ningún test pueda llevar una y olvidar la otra:

  1. @TestPropertySource carga bd-test.properties. Spring decide qué configuración gana por un orden de prioridad, y en ese orden una variable de entorno como SPRING_DATASOURCE_URL gana a los archivos application*.properties. En cambio, @TestPropertySource está por encima de las variables de entorno, así que nada externo puede redirigir los tests.
  2. GuardiaBaseDeTest, antes de Flyway. Justo antes de migrar, pregunta a PostgreSQL a qué base están conectadas las dos conexiones: la de Flyway (crea las tablas) y la de JPA (la que usan los tests). Spring permite que sean distintas con spring.flyway.url, así que comprobar solo una dejaría un hueco. Si alguna no es mitusalud_test, detiene los tests con el mensaje "Los tests solo pueden usar la base 'mitusalud_test', pero JPA está conectado a 'mitusalud'. No se ha modificado nada." Protege de despistes como editar mal el archivo.

Una anotación que agrupa otras se llama meta-anotación: Spring lee las anotaciones de dentro como si estuvieran puestas en el test.

Tests del repository: PesoRepositoryIT

Usan @DataJpaTest, que arranca solo JPA, Flyway y los repositories, contra un PostgreSQL real.

  • Por defecto @DataJpaTest cambiaría la base de datos por una en memoria. @AutoConfigureTestDatabase(replace = NONE) lo impide: una base de datos distinta podría dar por bueno algo que en PostgreSQL falla.
  • Cada test corre dentro de una transacción que se deshace al terminar: la base de test queda siempre vacía.
  • Al arrancar, Flyway aplica las migraciones y Hibernate valida la entidad contra la tabla. Si un script o una entidad tienen un error, fallan todos.
TestQué garantiza
Decimales exactos72.35 se guarda y se lee de PostgreSQL como 72.35.
Orden de la listaDel más reciente al más antiguo; el mismo día, el último registrado primero.
Peso absurdoAunque alguien se salte la validación Java, el CHECK de PostgreSQL lo rechaza. En el log aparece un aviso violates check constraint: es lo esperado.
La trampa de la caché de primer nivelHibernate guarda en memoria las entidades que ya conoce dentro de una transacción. Si guardas un objeto y justo después lo buscas por id, Hibernate te devuelve el mismo objeto de memoria sin preguntar a la base de datos, y el test pasaría aunque PostgreSQL hubiera guardado otra cosa. Por eso el test de decimales llama a entityManager.clear() antes de leer: obliga a hacer un SELECT real. Esta trampa la detectó una revisión mirando el log de SQL: el test solo hacía un INSERT.

Test de punta a punta: PesoApiIT

Usa @SpringBootTest, que arranca la aplicación completa, sin nada simulado: controller → service → repository → PostgreSQL. Registra un peso por la API, guarda el id que devuelve PostgreSQL y comprueba que la lista contiene ese mismo registro con su fecha y su peso. Buscar "cualquier peso de 71.8 kg" podría aprobar gracias a otro registro. Los tests de cada capa por separado no ven si las capas encajan entre sí; este sí.

@Transactional deshace todo al terminar. Funciona porque MockMvc ejecuta la petición en el mismo hilo y la misma transacción que el test.

CompruebaNo comprueba
Que controller, service, repository y PostgreSQL encajan: rutas, JSON, validación, transacción, SQL real.Una conexión HTTP real: MockMvc simula la petición sin red.
Que el dato sobreviva entre transacciones separadas: todo ocurre en una sola y se deshace.

Para cubrir lo de la derecha haría falta arrancar el servidor de verdad (@SpringBootTest(webEnvironment = RANDOM_PORT)) y usar un cliente HTTP real. Se añadirá cuando aporte algo; ahora sería sobredimensionar.

9. Cómo arrancarlo

Qué necesitas

  • En tu PC: Java 21, Git y un cliente SSH (Windows ya lo trae). Maven no: lo trae el wrapper.
  • En el servidor: Linux con Docker y Docker Compose, y acceso por SSH con clave.

Una sola vez, en el servidor

git clone https://github.com/canaritel/mitusalud.git
cd mitusalud
cp .env.example .env         # y pon una contraseña larga y aleatoria
chmod 600 .env               # solo tu usuario puede leerlo
docker compose up -d
docker ps                    # mitusalud-postgres debe aparecer como "healthy"

# Base de datos para los tests de integración (solo en el servidor de desarrollo)
docker exec mitusalud-postgres psql -U mitusalud -c "CREATE DATABASE mitusalud_test"

Para actualizar más adelante: git pull y docker compose up -d.

Cada vez que programes, en tu PC

Pon en la raíz del proyecto un .env con la misma contraseña que el del servidor. Después, dos terminales:

# Terminal 1: el túnel (déjala abierta)
ssh -N -L 5433:localhost:5433 usuario@servidor

# Terminal 2: el backend, desde la carpeta backend
cd backend
./mvnw spring-boot:run       # en PowerShell: .\mvnw spring-boot:run

Cuando veas Started MitusaludApplication:

  • Swagger UI: http://localhost:8080/swagger-ui.html
  • Salud: http://localhost:8080/actuator/health → {"status":"UP"}

11. Glosario

API REST
Forma de comunicar programas por HTTP usando rutas (/api/v1/pesos) y métodos (GET para leer, POST para crear…).
Endpoint
Una ruta concreta de la API con su método, por ejemplo POST /api/v1/pesos.
JSON
Formato de texto para intercambiar datos: {"kilos": 72.35}.
Entidad
Clase Java que representa una fila de una tabla (Peso).
DTO
Data Transfer Object: objeto que solo transporta datos entre la API y el código (PesoEntrada, PesoSalida).
Record
Clase de Java pensada para transportar datos: en una línea define campos, constructor, getters, equals y toString.
ORM / JPA / Hibernate
Un ORM traduce entre objetos Java y tablas. JPA es el estándar de Java para hacerlo; Hibernate es la implementación que usa Spring.
Spring Data
Genera los repositories a partir de interfaces y del nombre de sus métodos.
Transacción
Grupo de operaciones en la base de datos que se aplican todas o ninguna.
Migración
Script que cambia la estructura de la base de datos de forma controlada y versionada (Flyway).
CRUD
Create, Read, Update, Delete: las cuatro operaciones básicas sobre datos.
Contenedor / Docker
Un contenedor empaqueta un programa con todo lo que necesita para funcionar igual en cualquier máquina. Docker es la herramienta que los ejecuta.
Volumen
Espacio de disco que Docker guarda fuera del contenedor, para que los datos sobrevivan aunque se borre.
Túnel SSH
Conexión cifrada que lleva el tráfico de un puerto de tu PC a un puerto del servidor.
Starter
Dependencia de Spring Boot que agrupa todo lo necesario para una tarea.
Monolito modular
Una sola aplicación dividida en módulos con fronteras claras, que podrían separarse en servicios más adelante.
Arquitectura hexagonal
Diseño en el que las reglas de negocio no dependen de la base de datos ni de la web: se conectan con ellas mediante interfaces ("puertos") y sus implementaciones ("adaptadores").
Virtual threads
Hilos ligeros de Java 21: permiten atender muchas peticiones a la vez con código normal.
ProblemDetail
Formato estándar (RFC 9457) para devolver errores de una API en JSON.
i18n
Internacionalización: preparar la app para varios idiomas sacando los textos del código.
LTS
Long Term Support: versión con soporte y parches durante años. Java 21 lo es.
OpenAPI / Swagger UI
OpenAPI es el estándar para describir una API; Swagger UI es la página web que lee esa descripción y deja probar la API.
Healthcheck
Comprobación automática de si un servicio funciona (/actuator/health, el healthcheck de Docker).
